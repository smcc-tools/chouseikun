# 座席決め：決めた座席を確定して守る

作成日: 2026-08-13
対象: `日程調整アプリ/test/index.html`（座席決め）

## 背景

席を決めたあと、「もう一度シャッフル」を誤って押すと座席が上書きされる。確認も取り消しも無いため、決めた配置はその場で失われる。

現状の実装:

- `doSeatingShuffle` は確認なしで即実行し、`assignment` を上書きする（`test/index.html`）。
- 直前の配置は `assignmentHistory`（直近2件）に残るが、**席替えの重複回避にしか使われておらず**、復元の導線は無い。
- 席ごとの `locks`（🔒）はあるが、シャッフル対象から外すだけで手動の入れ替えは止まらない。全席をひとつずつ固定するのも現実的でない。

## 要件

| # | 要件 |
|---|---|
| R1 | 決めた座席を「確定」でき、確定中はシャッフルされない |
| R2 | 確定中はホスト向けの編集UIを座席画面から丸ごと隠す |
| R3 | 確定は次会ごとに独立している |
| R4 | 確定は解除でき、解除すると元の編集画面に戻る（座席は保持される） |
| R5 | 参加者の画面は確定の有無で変わらない |
| R6 | 共同ホストが古い画面を開いていても、確定中の座席は変更されない |

### 非目標（YAGNI）

- 複数案の保存・名前付き保存・案の見比べ
- シャッフルの取り消し（元に戻す）
- 確定した座席のスナップショットを別フィールドへ退避すること
- 確定と公開の連動（確定しても参加者への公開状態は変わらない）

## 方式

次会に確定フラグを1つ持たせる。

```
次会: { id, name, tables, assignment, locks, …,
        confirmed: true }     ← 追加。既定は未設定＝未確定
```

未設定を未確定として扱うため**移行処理は不要**。既存イベントはそのまま動く。

### 設計判断：既存の `locks` で代用しない

`locks` は「シャッフル対象から外す」意味しか持たず、手動の席入れ替えは止まらない。また「ホストが数席だけ固定した」状態と「全体を確定した」状態が同じデータになり区別できない。1席でも解除すれば確定が崩れる。別のフラグにする。

### 設計判断：確定時に座席のコピーを取らない

`confirmedAssignment` のような退避先を作ると、同じ座席が2箇所に存在し、どちらが正なのかが常につきまとう。確定中は座席を変える経路をすべて塞ぐので、`assignment` が壊れる余地がない。退避は作らない。

## UI

| 状態 | 座席表 | ホストツール（`#seatingHostTools`） | 座席表の下 |
|---|---|---|---|
| 配置なし | 空席 | 「席を決める（シャッフル）」 | — |
| 配置あり・未確定 | 入れ替え可・🔒あり | 「もう一度シャッフル」＋「この席で確定」 | — |
| 確定中 | 参加者と同じ（操作不可） | すべて非表示 | 確定バナー＋「確定を解除」 |

「この席で確定」は `assignment` があるときだけ出す。確定するものが無い状態では出さない。

### 解除ボタンは隠す領域の外に置く

確定バナーと「確定を解除」は `#seatingHostTools` の**外**（座席表の直下）に置く。中に入れると、確定した瞬間に解除する手段まで消えてしまう。

### 確認ダイアログは出さない

確定・解除とも座席のデータを壊さず、押し間違えても逆の操作で元に戻る。確認を挟む価値がない。

### 参加者側

確定の有無で表示は変わらない。バナーも出さない。確定はホストの誤操作を防ぐための仕組みであり、参加者に伝える情報ではない。

## 確定中に止まるもの

`#seatingHostTools` を隠すことで次が止まる。

- シャッフル（初回・再シャッフルとも）
- 卓の追加・削除・定員・上下振り分け
- メンバーの追加・削除・改名
- この次会の参加者（欠席）の切り替え
- 色タグ

加えて `#seatingResult` 側のホスト専用UIも出さない。

- 名前をタップしての席入れ替え
- 席のロック／解除（🔒）
- 卓の向きの変更・配置の調整

次会タブでは次を止める。

- **この次会の削除**（次会を消せば確定した座席も消えるため、守る対象に含める。解除してから削除する）

次会の名称変更と次会の追加は座席に影響しないので従来どおり行える。

## 守り方（3層）

表示を消すだけでは守れない。共同ホストがまだ古い画面を開いていれば、確定した直後でもシャッフルを押せる。

| 層 | 内容 |
|---|---|
| 表示 | `confirmed` なら編集UIを描かない |
| 操作 | シャッフル・席入れ替え・🔒切替の入口で早期 return（描画漏れの保険） |
| 書き込み | 書き込み時に読み直した `confirmed` を見て、真なら書かずに中断しトーストで知らせる |

書き込み層が本質的な防御になる。表示と操作の2層は、そこへ到達する前に気持ちよく止めるためのもの。

### 書き込み層をどこに置くか

座席まわりの書き込みは `updateActiveParty` に集約されている（欠席・入口・卓の行列・卓の追加削除・配置・ロック・席入れ替え・シャッフル結果の12箇所）。ここを塞げば座席の変更経路はすべて通る。

ただし現在の `updateActiveParty` は `latestEventData`（自分の画面が持つ写し）を見て書くため、**共同ホストが確定した直後は自分の写しがまだ古く、確定を知らないまま書けてしまう**。R6 を満たすには読み直しが要る。

そこで `updateActiveParty` を、次会の名称変更・削除で使っている `mutateParties`（トランザクション内で読み直し、対象を id で引く）経由に変える。`confirmed` の確認はそのトランザクションの中で行う。これで R6 を満たすと同時に、`updateActiveParty` の12箇所すべてが読み直しの恩恵を受ける。

メンバーの改名・削除だけは `updateSeating` を直接呼んでいるため、同じ確認を各々に入れる。

色タグは `seatTags` のみを書き `seatParties` に触れないため、書き込み層の対象外とする（表示層で隠れる）。

### 解除だけは通す

`mutateParties` の呼び出し側が「確定中でも通す操作か」を明示的に渡す。`confirmed` を偽にする更新かどうかをパッチの中身から推測すると、将来ほかのフィールドが増えたときに誤って通る。

## 変更する箇所

| 箇所 | 変更内容 |
|---|---|
| `isPartyConfirmed(party)`（新規・純粋関数） | `!!party && party.confirmed === true` |
| `renderSeating`（表示の親） | 確定中は `#seatingHostTools` を隠し、確定バナーを出す |
| `renderSeatingBoard` / 座席チップ描画 | 確定中はホストでも参加者と同じ描画にする |
| `doSeatingShuffle` / 席入れ替え / ロック切替 | 冒頭で確定中なら中断 |
| `updateActiveParty` | `mutateParties` 経由に変更し、トランザクション内で `confirmed` を確認 |
| `mutateParties` | 「確定中でも通す操作か」を受け取る引数を追加 |
| `seatingRenameMember` / `seatingDeleteMember` | 確定中なら中断（`updateSeating` を直接呼ぶ経路のため） |
| 次会タブの削除ボタン | 確定中は出さない |
| HTML | 確定バナーと「この席で確定」「確定を解除」ボタンを追加 |
| CSS | 確定バナーの体裁 |

`assignment`・`locks`・`assignmentHistory` の構造は変えない。Firestore ルール・権限まわりも変更しない。

## テスト

| 対象 | 内容 |
|---|---|
| `isPartyConfirmed`（新規・純粋関数） | 未設定・`false`・`true`・`null` の各ケース |
| `mutateParties` の確定ガード | 確定中は書き込まない／「確定中でも通す」指定なら通る／未確定は従来どおり通る |
| `mutateParties` の既存10件 | 変更なしで通ること（引数の追加が既存呼び出しを壊さない証明） |
| 既存の座席テスト | 変更なしで通ること |

### 実機検証（ヘッドレス）

1. シャッフル後に「この席で確定」を押すと、ホストツールが消え確定バナーが出る
2. 確定中は座席チップをタップしても入れ替わらず、🔒も出ない
3. 「確定を解除」で元の編集画面に戻り、座席は保持されている
4. 別タブ（共同ホスト）が確定前の古い画面のままシャッフルを押しても座席が変わらない
5. 参加者画面は確定の前後で変わらない
6. 1次会を確定しても2次会は編集できる
7. 確定中は次会を削除できない
8. コンソールエラー0件

## リスク

| リスク | 対応 |
|---|---|
| 確定中に解除手段を見失う | 解除ボタンを隠す領域の外（座席表直下）に置く。検証項目1・3で確認する |
| 表示の出し分けに漏れがあり、確定中でも操作できてしまう | 書き込み層のガードで最終的に止める。検証項目2・4で確認する |
| 確定を忘れたまま解散し、あとで誤シャッフルされる | 本設計の対象外。確定は任意であり、押さなければ従来どおりの動作 |
| 次会削除の抑止が過剰に感じられる | 解除すれば削除できる。2手になるだけで行き止まりにはならない |
| `updateActiveParty` をトランザクション化すると12箇所すべての書き込み経路が変わる | 既存の座席テストを変更せずに通すことを条件とする。実機検証で席入れ替え・卓の追加・配置調整・シャッフルの4経路を通す |
| `updateActiveParty` が非同期になり、直後に別の書き込みを行う箇所で順序が変わる | 連続して書いている箇所（シャッフル完了時の `assignment` と `assignmentHistory` は同一パッチ）を実装時に洗い出し、必要なら `await` でつなぐ |
